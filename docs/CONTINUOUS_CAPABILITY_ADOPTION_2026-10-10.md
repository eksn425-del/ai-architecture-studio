# K AI Studio — 持续吸收外部能力的产品迭代闭环（2026-10-10）

## 最终选择：双层机制，不是二选一

**A. 长期产品层（主动吸收）**：持续研究竞品流程和开源实现，把许可证允许、可靠、兼容、能改善通用体验的模块与设计方法吸收到自己产品的稳定能力目录。包括 Agent Skill、构造器、状态管理、版本恢复、质量审查、缓存和用户交互；并不等待某个用户来问才看。对当前产品功能有效的改动要真正进入**默认工作流**或有明确的按条件启用策略，不仅是 README 或可选 ZIP。不能因此破坏用户已有功能。

**B. 运行任务层（按需选择）**：真实任务到来时，根据输入、约束、质量与成本要求，从产品已经掌握的能力中选择合适实现。不是每轮都用所有开源库；如果某个新库不适用，应有可核查理由，并使用稳定 fallback。真实执行必须产生来自宿主/执行器的调用凭据；不凭 Agent 自述判断是否使用。

只有 **A 持续建设能力 + B 在真实任务调用**，才能形成用户实际得到的长期正反馈。适用于以后的网站、CAD、视频、文档、建筑生成等项目，不能用「开源越多越强」替代可靠质量。

## 五段漏斗（从此不要混为一谈）

1. `researched`：源项目分析清楚优势、源码、许可、版本、适用任务。竞品闭源时只能学习可观察的流程和合法模式，不得复制未授权代码。
2. `installed / exposed`：可信版本已下载/集成且能在产品中调用。证明**可用性**，不是改善了用户结果。
3. `smoke_verified`：组件通过隔离环境功能测试、API / 兼容性测试。证明它能够运行。
4. `product_used`：在**真实产品任务**中，选用合适实现并有当前真实执行器生成的调用记录和提交/输出证据。零调用 = 未实际使用。
5. `effect_verified`：模型、网页或视频结果按任务标准被审查，能明确说明改善了什么、有哪些残留缺陷与成本；不能仅靠执行成功认定质量提升。

不适用、许可证不符合或兼容失败的路线可记 `rejected`（附证据）；并不意味着产品退步。

## K AI Studio 已落地的第一版代码机制

- `app/oss_method_catalog.py`：可检索的具体方法目录（提供者、仓库、许可证、代码入口、任务适用条件、fallback）；由 `app/agent_tools.py` 注入真实 Agent Ruby 工具说明。
- `app/construction_strategy.py`：新计划可提供每系统的具体 `method_id`、`selection_reason`，向后兼容旧计划。选择实现是**规划**，不能当成使用证据。
- `app/oss_method_runtime.rb`：在同一受保护 SketchUp 事务里包装现有 SAIE 和获许可启用的 ADAI 几何方法，记录函数 ID、调用结果、耗时、错误类。该模块不是第二写者。
- `app/project_ruby.py`：将调用记录写入当前 SKU owned-root 元数据并在提交后独立读回；为本次 script SHA、revision、root PID 附带 `oss_method_ledger` 和 `oss_method_adoption`。无匹配记录会显示 `missing_or_unverified` 而非假成功。读回可归因于**脚本修订**，还需要具体对象/源图审查才能确认质量。
- `app/image_to_sketchup_skill.py`：提示 Agent 在自写 Ruby 之前确认 SAIE/ADAI 是否更适用；可按情况解释 fallback，不强制无关库被调用。
- `scripts/validate_test_evidence.py`：2026-10-10 起的真实建模结果必须上传 `model/oss-method-ledger.json` 和 `model/oss-method-adoption.json`，包括诚实的零调用。缺少证明或自相矛盾不能通过 GitHub 证据完整性检验。
- `.github/workflows/oss-method-adoption.yml`：Python＋Ruby 回归测试；`tests/test_oss_method_adoption.py` 强制区别选择、烟测、正式执行和视觉质量。

当前为**远端代码与 CI 已验证的开发集成**，Windows 真 SU2024 接入新日志功能、默认运行环境、用户图片建模质量**必须在下一轮 Codex 现场验证**，不能把此文件当作新模型已经变好。

## 每次用户提供新的开源项目 / 竞品材料

直接在唯一产品仓库开展“合法检索→源码/演示审查→实际能力缺口→能力采纳→真实使用→效果跟踪”。

记录一个简单的能力决策，尽量不创建散乱的新产品：
- 什么用户痛点？是否在真实失败证据中存在？候选优势是什么？
- 哪段代码/方法值得**直接吸收进基础能力**？许可证是否允许？版本、平台是否匹配？
- 运行时是否必须全局默认调用，还是只有特定任务需要？选哪个能力、为什么？
- 要修改现有 Agent 规则/调用器/可执行 Skill/测试中的哪个真实位置？仅 README、下载器或 ZIP 清单不算最终交付。
- 怎么证明真实运行？执行器的调用结果、成本、截图、项目对象和失败记录在哪？
- 结果是否优于现有产品？如未改善，为什么？保留成功方案、废弃或回退失败方案，避免技术债。

## 通用质量标准（跨领域）

**3D / CAD：** 可编辑原生文件、尺度/拓扑/视图、局部修改安全、专业合法合规审查（施工图不能仅靠 AI 口头通过）。

**AI 建站：** 真实浏览器操作、用户任务成功、跨设备可用性、性能、回退、访问权限和测试截图，不只展示 UI。

**AI 视频：** 多镜头人物/物件一致性、时长、时序、生成成本、用户授权素材处理、可播放文件与复现记录。

所有领域的门槛相同：**不是库数目增加，而是最终用户体验、质量、稳定性、速度或成本有真实的进步证据**。
