## 用户操作和界面

用户上传同一建筑近正面及右斜视，正常中文要求还原、接受估算、确认建模，然后请求继续优化。没有技术提示注入。计划摘要确实已出现在主对话，但详细参数另放输入区域上方小浮层，导致阅读割裂。`app/static/assistant.css:44–46,66` 的绝对定位、宽度 `min(620px,70vw)` 和高度 `45vh` 是直接原因。不是用户应该适应的必要流程。建议主聊天展示可读计划与一次批准，完整工程账本作为可选资料；不自动弹出覆盖聊天的长文浮层。

用户贴出的参数卡末尾出现字面量 `` `n ``，是持久化笔记的换行写法错误；详细卡还保留“未编辑模型”旧段，与追加执行记录矛盾。应更新版本/状态，不能让用户辨读内部账本。

## 原因定位

1. **主体几何失败**：识别文字提到了正确特征，但脚本以手填坐标拼板/柱/玻璃，没有可靠校准两视角的轮廓、凹口深度、屏风包覆和楼梯端点。两图足以约束已见主体，不需要把这些错误归咎于背面缺图。
2. **代表构件审核不足**：原型被复制成大量屏风之后仍在替换孔板拓扑和材质。完整展开遍历 SCREENS 包含 383,158 面/1,146,804 边；这是实例展开数，**不是独立存储面数**。细孔工程早于主体可靠性，几何成功不等于远景视觉正确。
3. **质量回路没有完成交付**：独立 Critic 实际指出主形/屋顶/交通错误，模型仍失败；修正效果未完成便遇到超时/预算。不能说没有 Critic，也不能说有 Critic 就自动修好。
4. **运行缺陷**：写后 GUID 错误、几何异常与重复上下文挤占有效时间。单纯调大预算不能解决主体错误。
5. **不能单凭此实验判定 Sol Low 本身无能力**：当前可确认的是本产品 Agent 在本模型档位下失败；尚未做同输入、同能力、同预算的直接模型对照，无法把模型能力与 harness 影响量化拆开。
